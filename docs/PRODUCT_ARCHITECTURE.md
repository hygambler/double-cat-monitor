# 产品目标与分阶段架构：双猫生活行为监测

更新：2026-11-13。整理与维护：Mac 端 agent（Codex），与 PC 端 agent 共同参与设计、实现、测试及文档交接。

本文记录用户新增的长期目标及推荐设计。除当前 PC 基线已有功能外，以下模块均为待实施方案，不代表已部署或已经取得准确率、功耗结果。

## 1. 用户目标与现有起点

最终目标：在单房间内，用多个摄像头识别两只猫，分别统计吃粮、喝水、上厕所次数；研究排便/排尿区分；低功耗长期运行、停机恢复和断流重连；支持摄像头追踪；制作手机远程访问的美观工作台。

现有设备是 Windows 10 / i7-9700KF / RTX 4060 PC 与 Logitech C920。当前仅完成单路粮碗区域候选进食监测，详见 [项目状态](../PROJECT_STATUS.md)。不假定已购买第二台摄像头、低功耗主机、MCU、云台或滑轨。

当前算法可靠性优化先按 [夜间身份连续性研究方案](NEXT_STEPS_RESEARCH.md) 推进。产品扩展应保留这一基线，避免同时改样本、识别、相机和事件规则，无法解释结果。

## 2. 推荐的最终分工

```text
固定镜头：粮碗 / 水碗 / 猫砂盆（数量按可见性确定）
  → 每路独立采集、时间戳、断流恢复、画质状态
  → 共享推理调度：猫检测/分割 → 轨迹 → 个体身份
  → 各站点行为识别与事件状态机
  → 事件存储 + 设备健康 + 可选事件片段
  → 本地 API → 手机网页/PWA → 后续按需原生 App

可选追踪镜头 → 追踪目标选择 → 云台/滑轨控制器
                              ↕
                    MCU：电机、限位、看门狗、传感器
```

推荐将低功耗视觉主机与 MCU 分工，而非把整套 Python / YOLO / SQLite / Web 应用直接装入 MCU。先在 PC 验证算法，再比较低功耗 Linux 主机、带 NPU 的板卡或智能相机，MCU 负责实时控制。设备尚未选型，不承诺某块板支持当前完整模型或多路吞吐。

MCU 视觉仍保留为后期研究分支：例如单路小模型、事件唤醒、简单分类或分布式预筛选，再由主机融合。Espressif 当前官方模型库已列出 ESP32-S3 / P4 等平台的量化 YOLO26 检测示例；因此不能笼统说“MCU 不能跑 YOLO”。但官方特定配置中，640 输入 YOLO26n 的纯模型时间约为 P4 1.52 秒、S3 3.79 秒；这是厂商示例数据，不是本项目测量，也不是 YOLO26n-seg + 双猫身份 + 多路解码 + 行为识别的整体性能。模型能运行不等于完整系统满足需求。

参考：[ESP-DL 模型库](https://github.com/espressif/esp-dl/blob/master/models/README.md)、[YOLO26 示例与基准](https://github.com/espressif/esp-dl/blob/master/models/yolo26/README.md)。查阅于 2026-11-13；后续选型必须锁定代码、模型和硬件版本后复测。

## 3. 多镜头与追踪的取舍

优先固定监测粮碗、水碗和猫砂盆，使关键行为始终可见。三处可以由一台或多台镜头覆盖，取决于机位、遮挡和目标像素尺寸；不能仅根据房间数量确定相机数量。

云台或滑轨作为可选追踪视角。单镜头追猫转走后，原区域可能发生另一只猫的行为；它不能替代多个关键点的同时观测。追踪优先级、人工接管、丢失目标后回预置位应独立设计。固定镜头担任全景定位、追踪镜头获取细节，是可以后续验证的组合。

移动镜头会改变 ROI、透视和背景。不同预置位需独立标定；运动中暂停依赖固定 ROI 的统计，停稳后验证标定。相机主动移动不应触发现有“机位偏移”故障；应显式标记预期移动状态。

可编程云台需要核实公开接口及具体动作能力；支持 RTSP 只说明可取流，支持 ONVIF 也不保证设备实现全部 PTZ 功能，见 [ONVIF 官方说明](https://www.onvif.org/blog/2023/11/13/how-to-use-onvif-profiles-to-ensure-interoperability/)。不假定 DJI Osmo Mobile 4 / SE 可用 Python 控制。

自制云台先验证负载、独立供电、角度反馈或校准、死区、限速、机械限位和断线停止。滑轨额外增加回零、端点开关、线缆拖链、夹点防护和行程校准，建议排在云台实验之后。电机命令必须有有效期，通信中断后不继续执行旧命令。

## 4. 吃、喝、上厕所的算法边界

| 层级 | 能回答的问题 | 尚需补充的证据 |
| --- | --- | --- |
| 猫检测 | 画面有没有猫 | 遮挡、低光与小目标测试 |
| 身份与轨迹 | 当前观测对应哪只猫 | 夜间样本、轨迹融合、交接场景 |
| 区域到访 | 是否进入粮/水/猫砂区域 | 各站点 ROI 和事件真值 |
| 行为分类 | 是否确实进食、饮水或排泄 | 动作序列、足够清晰的局部细节和人工标注 |
| 排泄类型 | 排便、排尿、两者都有或无法判断 | 专用视角、整段视频及可靠结果核对 |

每一层都保留 unknown。不要把“进粮区”直接升级成“吃了一次”，也不要把“进猫砂盆”直接算一次排尿。

排便/排尿作为独立行为研究：如果“形状”指身体蹲姿，应结合背部、尾部与后肢姿态的时间变化、持续时间、刨砂/掩埋序列；如果指排泄物形状，可研究可见粪便及尿团的前后画面对比。二者都会受猫身体遮挡、猫砂覆盖、红外画面和视角影响，单张轮廓不作为可靠真值。

建议先做“猫砂盆到访次数/时长”，再标注并试验“排便 / 排尿 / 两者都有 / 无排泄或其他 / 无法判断”的事件级分类。行为识别可尝试小型序列分类器，不假设现成 YOLO 猫类别已经具备这些标签。COCO 人体姿态模型也不能直接当作猫骨架模型。

事件可以包含多个排泄子行为；到访次数与排便/排尿次数分别定义。看不清时记录待复核，训练和测试按日期/片段分开；排泄类别不均衡时分别报告每类精确率、召回率和未知比例。相关既有研究可参考 [Multi-Cat Monitoring System Based on Concept Drift Adaptive Machine Learning Architecture](https://pmc.ncbi.nlm.nih.gov/articles/PMC10648833/)，不将文献结果当作本项目已实现指标。

当前目标是行为统计；饮水量、排泄量、疾病判断不是本阶段已具备能力。称重等辅助传感器作为可选对照来源，是否采用由后续误差与成本决定，不预设采购。

## 5. 低功耗设计

先记录 PC 整机待机、单路监控、后续多路监控的墙上功耗、实际帧率及事件准确性。降低推理频率不代表视频解码和整机功耗同比下降；不能只看 GPU 利用率判断节电。

拟采用三级运行：低频巡视 → 触发后较高频识别 → 事件结束后回到巡视。先试验低成本画面变化或小模型触发，并保留周期推理和事件内保持时间，避免静止低头吃喝被当作无人。CPU / GPU、输入尺寸、量化和硬件解码每次单独对照。

若希望 PC 完全休眠，需要另一台常开设备发现事件并唤醒，且测量唤醒延迟带来的遗漏。最终低功耗主机更适合保持小负载在线，而不是假设完全关机仍能监测。

估算持续供电月耗电：平均功率 W × 24 × 30 ÷ 1000；年度电费节省与新增硬件成本一起比较。所有相机、主机、电源及可选电机都计入总功耗，不预先指定未经测量的瓦数目标。

## 6. 停机、断流和恢复

区分摄像头断流、单采集进程卡住、推理异常、应用崩溃、系统重启/休眠和断电。拟增加系统级启动/守护，心跳与无新帧超时，有限退避重连，每路独立健康状态；一台相机离线不拖死其他路。

活动事件需持久化并带唯一 ID。异常中断标记 interrupted 和最后有效观测时间，恢复后开始新轨迹；不得将离线时段当作持续行为。重试写库/上传使用幂等键防重复。正常停止释放摄像头并安全提交数据库，断电后检查数据库和未完成事件。

先适配 Windows 的启动方式和摄像头会话，再在低功耗 Linux 端做服务守护；不能假定 USB 摄像头在所有 Windows 后台服务会话中行为一致。验收应包含拔插、断网、强制终止、重启和模拟断电恢复；日志轮转、存储限额、数据库备份及恢复也属于常开能力。

## 7. 手机工作台与远程访问

近期保留 Streamlit 作为算法调试与人工复核台；先让手机在外网通过私有网络访问现有页面，验证真实需求。可评估 Tailscale + Serve，在授权网络内用 HTTPS 访问本地服务；需要手机和主机配置客户端/账号及访问规则，网络可达性需实测。参考 [官方 Serve 文档](https://tailscale.com/docs/features/tailscale-serve)。本次没有安装或开通远程访问。

产品界面建议先做自适应 PWA（可添加到手机桌面的网页），减少同时维护 iOS / Android 原生应用的成本。推荐页面为：双猫今日卡片、吃/喝/上厕所时间轴、近 7/30 日趋势、事件片段与人工复核、摄像头/主机在线状态、设备与隐私设置。明确区分真实记录、未知身份、候选行为、已确认行为与离线空窗；不用零次数表示没有数据。

后续将采集/推理与展示解耦，由本地 API 提供数据，保持现有事件记录可迁移。SQLite 可先保留，由单一写入服务处理多路事件，避免直接复制多个采集进程争抢当前锁。实时预览按需开启、限制帧率和带宽，历史统计不依赖持续视频直播。

应用账号、会话和权限与网络访问分开设计。若以后需要无需私网客户端的公网登录，再单独设计 HTTPS 网关和认证；不直接把 Streamlit、数据库或摄像头端口转发到公网。相机密码和会话密钥不进 GitHub。默认本地推理，媒体保留期/删除策略可配置，离线不能伪装成最新画面。

## 8. 数据接口先行，硬件后定

建议后续新增或迁移的字段：camera_id、station_id、session_id、track_id、事件唯一 ID、UTC 观测时间、事件类型/证据级别、原始/融合/人工身份、结束原因、离线区间、模型及配置版本。轨迹超时使用单调时间，历史跨设备记录统一时间与时区；多设备对时失败需可见。

跨摄像头 track_id 不保证相同；同一站点两台镜头看见同一次到访要去重，不同站点事件则独立。先做单站点单镜头，再增加可控重叠场景，不将同名猫同时出现视作自动正确关联。

部署拆分为采集适配器、模型推理接口、轨迹/身份层、行为事件层、数据库/API、前端和电机控制协议。先抽出稳定边界，再逐项迁移；不为长期目标立即重写整个项目。

## 9. 实施顺序与验收门槛

| 阶段 | 使用设备/工作范围 | 交付与推进条件 |
| --- | --- | --- |
| A：当前算法可靠 | 现有 PC + C920；夜间诊断、身份连续性对照 | 有标注片段及错名/未知/漏记的可重复基线 |
| B：长期运行与手机初访 | 同一套设备；恢复机制、功耗基线、私有远程访问 | 完成故障注入；连续运行 24 小时再到 7 天；报告离线和恢复时间 |
| C：多站点 | 先评估现有视角，再决定是否增加镜头 | 吃/喝/猫砂盆到访独立统计；并发、站点去重与身份交接验证 |
| D：行为与产品界面 | 标注动作序列；API 与手机 PWA | 候选/确认行为分开；排泄类型逐类验收，允许未知；手机可复核 |
| E：低功耗迁移 | 按实测负载评估候选主机/智能相机/MCU 分工 | 同一测试集的精度、端到端延迟、总功耗、价格及恢复能力对照 |
| F：主动追踪（可并行研究） | 明确接口的云台；滑轨更后置 | 回零/限位/断线停止和丢失回位合格，固定站点统计不因追踪丢失 |

阶段顺序可按现场需求调整；原生 App、整套 MCU 移植和滑轨不作为近期运行的前置条件。下一项工程任务仍建议 A：可追溯的夜间诊断和基线评估；同时把 B 的恢复故障清单纳入设计。新增采购须等视角、算力、功耗和部署兼容性证据明确后再决定。

每次 Mac / PC 接续先读 GitHub 最新提交与项目状态；实现使用明确版本和测试交接，Windows / CUDA / C920 现场结果由 PC 验收。本次仅补充产品设计，未修改运行代码、配置或安装任何新组件。
